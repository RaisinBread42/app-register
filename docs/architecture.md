# Architecture

## What the app does

App Register is an application health and lifecycle monitoring service for lean IT teams (1–5 people). It tracks bought SaaS and in-house apps with named owners, watches their dependencies, hosting, vendor notices and renewal deadlines, ties each change to the apps it affects, and surfaces the next useful action. A Governance Board summarises it all for managers and executives. The spec is [docs/product/spec-v1.md](product/spec-v1.md), and the decisions are in [docs/product/gap-analysis.md](product/gap-analysis.md).

## How a request flows

Browser → Next.js App Router (`src/app/`) → server actions or route handlers → domain services (`src/lib/services/`) → Drizzle (`src/lib/db/`) → Postgres 18.

JSON API: route handlers in `src/app/api/` ([api.md](api.md); OpenAPI spec in `src/lib/api/openapi.ts`). Every handler goes through `handle()` in `src/lib/api/http.ts`: bearer API key → workspace, `Idempotency-Key` on POST/PATCH, errors → `{ error }`. No response is stored for an `Idempotency-Key`: each POST/PATCH route names the row it answered about (`RESOURCE_KIND` + id; an import adds its counts), `idempotency_keys` keeps that with the status code, and a repeat is answered by reading the row again (`src/lib/api/replay.ts`). Services only touch rows in that workspace.

UI (`src/app/(register)/`): server components load data and server actions submit it, both through `src/lib/ui/api-client.ts`, which calls `${APP_URL}/api/*` over HTTP with `APP_REGISTER_API_KEY`. Client components never call the API and never see the key. Each POST/PATCH sends an `Idempotency-Key` that the page rendered for that user action, so a double-click or retry of one Save is one write. `src/proxy.ts` puts every non-API route behind HTTP Basic auth with `UI_PASSWORD` (fails closed when unset); `/api/*` keeps its bearer keys.

Dependency monitoring (`src/lib/services/dependency-health.ts`) reads two free, keyless sources: the npm registry for the latest version of each package and OSV.dev for known advisories. All outside calls go through one module, `src/lib/services/package-sources.ts` (tests pass it a fake `fetch`; `src/test-setup.ts` blocks the real network). Only package names and versions are sent, and nothing that comes back is trusted: answers are size-capped and shape-checked there, and every advisory goes through `src/lib/services/advisories.ts` on the way into the database. Advisories are rows, not a list on the dependency: `dependency_advisories` holds one row per advisory (`manual` for an id a person recorded, `osv` for one the check found) and `dependency_advisory_aliases` its other ids; `src/lib/services/dependency-advisories.ts` reads and replaces them, and the API still answers `vulnerabilities` and `advisories` lists built from those rows. A check runs after an import or a manual change, and for every active app when the daily job posts to `/api/monitoring/refresh` (both checks; `/api/monitoring/dependencies/refresh` runs this one alone); it always runs after the write has committed (`afterCommit` in `handle()`), never inside a database transaction. The health score (`src/lib/services/health.ts`) is 100 minus each dimension's deductions; a dimension plugs in with one line in `REPORTERS`. `dependencies` and `hosting` report; `licence` and `pricing` do not yet.

Hosting monitoring: `src/lib/hosting-catalog.ts` lists the providers and services the add-hosting dialog offers and how each is watched. `src/lib/services/hosting-monitor.ts` (the hosting check) reads only free, keyless public sources through `src/lib/monitoring/` (tests pass a fake `fetch`): endoflife.date for end-of-support dates (`monitoring/end-of-life.ts`; a version that matches several releases takes the earliest date and sets `is_version_inexact`), Statuspage `summary.json` for Vercel, Cloudflare, Netlify and GitHub, Google Cloud's `incidents.json`, AWS Health's `public/currentevents`, and the Azure status RSS feed. It follows the same rules as dependency monitoring: one fetch module (`monitoring/http.ts`: 8 s timeout that also cuts off a body still arriving, via `src/lib/capped-body.ts`, `User-Agent: app-register`, answers capped at 4 MB, redirects refused, each URL once per run, six at a time); only catalog values are sent; each feed is parsed once per run into what rows are matched against (`monitoring/status-feeds.ts`: the catalog services each incident lists, read from its whole list, and the regions it names), so matching a row is a few lookups; nothing that comes back is trusted (`monitoring/feed-values.ts` type-checks, cleans and cuts every value, and every incident goes through `normaliseIncidents` in `src/lib/services/hosting-incidents.ts` on the way into the database, which also drops any link that is not `https:` on the provider's own status host; the link is checked once more when it is read). Incidents are rows, not a list on the hosting row: `hosting_incidents` holds one row per incident, in the order the check stored them; `hosting-incidents.ts` reads and replaces them, a check replaces a row's incidents in the same transaction as its conditional update of the row, and the API still answers an `incidents` list built from those rows; the check after a write runs in `afterCommit` with the shared 15 s budget, never inside a transaction; and an answer is only stored while the row still is what was checked and its app is still active. `src/lib/services/hosting-health.ts` turns what the check stored into the `hosting` deductions of the health score and each row's own status. Limits: public status pages only show incidents the provider chooses to publish, never account-specific ones (Azure Service Health and the AWS Health API need the customer's own cloud credentials and are not used); Azure's feed is prose with no severity or service list, so matching is by service names and full region names in the text (`monitoring/regions.ts` turns region codes, availability zones and display names into one key per region); a row typed as free text is not monitored; and the check runs on save, on demand and when a scheduler calls `POST /api/monitoring/refresh`, not continuously.

Notices (`src/lib/services/notices.ts`, spec §3 P0): durable records of what changed or is due, derived from what the checks stored. `noticesForApp` turns an app's dependencies (OSV advisories, ids a person recorded) and hosting rows (end of support within `END_OF_SUPPORT_SOON_DAYS`, provider incidents) into notices with a dedupe key, plus a match for the app: the component, version and region it matched on, the reason in words, and a confidence (an incident that doesn't name the app's service or region is `low`, spec §8 check 22). `syncAppNotices` upserts by `(workspace_id, dedupe_key)` and `(notice_id, app_id, component)`, and marks matches the app no longer has as `resolved_at`; a notice with no open match left gets `resolved_upstream_at`. Nothing is deleted. It runs after every dependency or hosting check, after removing a dependency or hosting row or editing a hosting row, in the daily refresh (all active apps), and at start-up as an idempotent backfill (`scripts/db-migrate.ts`). `notices` and `app_notice_matches` are relational; `origin` tells an outside claim (`external`) from a fact a person entered (`person`). Read API: `GET /api/notices`, `GET /api/notices/:id`. Actions (`src/lib/services/notice-actions.ts`, [26]): each match has a status (new, reviewing, snoozed with a date and reason, handled with evidence) and an assignee; a check never writes those columns. Every action appends a row to `audit_events`. It is append-only: triggers in `drizzle/0009` refuse UPDATE, TRUNCATE and direct DELETE, and allow only a workspace cascade or a retention job that sets `app.audit_retention`. Rows are ordered by a database sequence (`seq`). The actor (`src/lib/services/actor.ts`) is the API key, by name and id, until people sign in ([37]). Undo rebuilds the previous state from the timeline and writes a new event. A handled match that the source reports again reopens (actor `System`).

UI uses Meta Astryx components only (Obsidian theme in `src/themes/obsidian/`, edited with the theme editor in `themes/obsidian/`). Screens mirror `docs/design/app-register-prototype.html`; parts with no API yet (licence and pricing checks, sources) show a muted coming-soon state, never made-up numbers. Business rules live in services, not in React components.

## Rules that are not obvious from the code

- Prefer `npx @astryxdesign/cli component <Name>` (or the `astryx` npm script) over guessing Astryx props.
- Pin `@astryxdesign/*` versions; see [ADR 0001](adr/0001-stack.md).
- Seed and demo data must be fictional — never real company, client, or employer data.
- No magic strings for statuses, kinds, routes, or alert offsets: put them in `src/lib/constants.ts`.
- Every table except `workspaces` carries `workspace_id`; children reference parents by `(id, workspace_id)` so a row can never point into another workspace. One default workspace until sign-in exists.
- Relational data only: no `json`/`jsonb` columns, no array columns and no serialised JSON in a text column; a list becomes a child table (see `dependency_advisories` and `hosting_incidents`), and a test in `src/lib/db/schema.test.ts` fails on any JSON or array column.
- Allowed values are `text` plus a `CHECK` built from the arrays in `src/lib/constants.ts` (no Postgres `ENUM`).
- Ids come from `newId()` (`src/lib/db/ids.ts`), never a DB default. `updated_at` is set by Drizzle `$onUpdate`, so all writes go through services.
- Apps are soft-deleted (`archived_at`); active-app queries share one filter in `src/lib/services/apps.ts`.
- Schema change: edit `src/lib/db/schema.ts`, `npm run db:generate`, write the inverse in `drizzle/rollback/`, call it out in the PR.
- Unit tests use `createTestDb()` (`src/lib/db/test-db.ts`): a fresh in-memory PGlite built from the real migrations.

Source freshness ([31], spec §8): `src/lib/services/source-checks.ts` stores each source's last attempt, last success and last error (`source_checks`, one row per workspace and source) from every dependency and hosting check. `listMonitoringSources` reads them (status, last answer, last error, the apps that rely on each source). Health marks a dimension and the app `stale` when a source behind it failed after a good reading (`staleSince`), so the last valid reading is kept but never shown as healthy.
